# Termux → настоящий `kimi acp`

## Почему мост, а не «просто запустить»

Android запрещает приложению А исполнять бинарь из песочницы приложения Б. У Termux свой
uid, свои библиотеки (glibc вместо Bionic) и свой mount namespace: `ProcessBuilder` из
Agent Phone до `node` и `kimi` внутри Termux не дотянется — никакими правами. Это не
недостаток кода, это модель безопасности системы.

Единственный разрешённый канал между двумя приложениями на одном устройстве — loopback:

```
Agent Phone                          Termux
AcpSocketAgent ── tcp 127.0.0.1:8712 ──> kimi-acp-bridge.mjs ── stdio ──> kimi acp
   (AcpTransport, NDJSON)                    (один кадр = одна строка)
```

`AcpTransport` построен на `BufferedReader`/`BufferedWriter`, поэтому голый TCP вставляется
в него без единой новой зависимости: ни OkHttp в APK, ни `ws` в Termux. WS-вариант
(`kimi-acp-bridge-ws.mjs`) лежит рядом только для отладки трафика из браузера.

## 1. Termux

Ставить **не** из Google Play (та сборка заброшена и не обновляется). Нужен релиз с GitHub:

    termux-app_v0.118.3+github-debug_arm64-v8a.apk
    sha256 72fdb596045116bf5ba1b5bdf5b26fddb9acc0bd074ad9f2da9eb0ae85e83a4e

После установки открыть Termux **один раз** и дождаться, пока он распакует bootstrap
(первый запуск — это несколько минут молчания, не трогать).

Xiaomi/MIUI/HyperOS убивают фоновые процессы, и мост умрёт молча посреди сессии. Сразу
включить: `termux-wake-lock`, а в настройках системы — Батарея → Termux → «Без
ограничений» + автозапуск.

## 2. Node + Kimi + проверка моста

Одной командой внутри Termux:

    curl -fsSL -H "Accept: application/vnd.github.raw" \
      "https://api.github.com/repos/Flawl3ssss/agent-phone/contents/tools/termux/setup-kimi.sh?ref=main" | bash

Это не придирка к красоте: на этом же устройстве `raw.githubusercontent.com`
не резолвился вообще, а `api.github.com` отвечал. Если API недоступен, вариант
обычный — `curl -fsSL https://raw.githubusercontent.com/Flawl3ssss/agent-phone/main/tools/termux/setup-kimi.sh | bash`.

Скрипт ставит Node LTS, локально (не `-g`) тянет `@moonshot-ai/kimi-code` и ACP SDK,
качает инструменты и **обязательно прогоняет selftest моста против мока** — до всякого
Kimi. Смысл порядка: если падает selftest, виноват Termux/Node, а не протокол, и искать
надо в другом месте. Проверка ничего не стоит: ни токенов, ни сети, кроме загрузки.

Дальше руками (оба шага интерактивные):

Как именно входить — **подтверждено живым Kimi 0.42.0** (CI-прогон G3′,
`authMethods: [{"type":"terminal","id":"login","args":["--login"]}]`):

    ~/agent-phone/node_modules/.bin/kimi --login

Это terminal-метод: агент сам печатает ссылку/код подтверждения, браузер
открывается на этом же телефоне. Отдельно заранее входить можно не всегда —
ACP-`authenticate` с methodId `login` делает то же самое изнутри сессии, и
зонд ниже пробует именно его; но на телефоне `--login` в терминале надёжнее,
потому что не зависит от того, пропустит ли агент аутентификацию в ACP.

## 3. Настоящий Kimi против протокола (гейт G3′ на живом агенте)

    cd ~/agent-phone
    KIMI_BIN=$HOME/agent-phone/node_modules/.bin/kimi ACP_CWD=$HOME PROBE_PROMPT=1 \
        node tools/acp-live-probe.mjs

Имя переменной — `KIMI_BIN` и ничего другого: зонд сам дописывает аргумент `acp`.
`ACP_AGENT_CMD` в пробе нет, и с ней зонд тихо запустил бы `kimi` из PATH — а это
совсем другой бинарь и обидная «победа».

Зонд сверяет заявленные capabilities с документированным контрактом и прогоняет полный
ход. Это единственный шаг, который тратит токены, и единственный, который доказывает,
что наши предположения о Kimi верны — мок их не доказывает.

## 4. Мост + приложение

    node ~/agent-phone/tools/termux/kimi-acp-bridge.mjs
    # BRIDGE_DEBUG=1 — печатать каждый кадр;  BRIDGE_PORT=9000 — другой порт

Терминал с мостом держать открытым (см. пункт про MIUI). В Agent Phone — тап по чипу
режима в шапке → «kimi · Termux». Выбор сразу переподключает сессию.

Сессия = одно соединение = один процесс `kimi acp`. Разорвали соединение — мост убивает
агента (SIGTERM, через 3 с SIGKILL), чтобы на телефоне с 512 МБ не плодились сироты.

## Диагностика

| Симптом | Где искать |
|---|---|
| Приложение: «мост не отвечает на 127.0.0.1:8712» | Мост не запущен или упал. В Termux: `ps aux \| grep bridge`. MIUI мог убить процесс |
| Selftest моста падает в Termux, а на хосте зелёный | Сборка Node/ Termux, а не протокол. `bash setup-kimi.sh --check`; чаще всего помогает `termux-change-repo` |
| Мост запущен, но приложение молчит | Порт/адрес: в Termux `ss -tlnp \| grep 8712`; в приложении порт должен совпадать |
| Соединение есть, handshake не проходит | `BRIDGE_DEBUG=1 node …` — видно, долетает ли `initialize` и что отвечает агент |
| Агент умер в середине хода | Мост печатает хвост stderr Kimi — там настоящая причина (выход токена, OOM, обновление CLI) |
| `kimi: Unknown builtin module` / EACCES при установке | Не использовать `-g`: скрипт ставит локально в `~/agent-phone/node_modules` |

## Границы того, что это даёт

- Мост и транспорт слушают **только** `127.0.0.1` и не имеют аутентификации. ACP в
  открытом виде, поэтому `BRIDGE_HOST=0.0.0.0` — это «любой в сети отдаёт команды вашему
  агенту с доступом к файлам». Не делать так без явной причины.
- Токен Kimi лежит в конфигу Termux, а не в хранилище ключей приложения.
- Порт жёстко задан по умолчанию; если на устройстве уже что-то слушает 8712, мост честно
  говорит `EADDRINUSE` и просит `ss -tlnp`.
